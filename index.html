98 billion pixels, one zip file, and the road to a GeoTIFF

New York City's 2017 land cover map labels every half-foot of the five boroughs. This page walks through how that data is packed into Land_Cover.zip, how a GeoTIFF stores a raster, and how resample.py turns one into the other without ever unzipping.

The original zip

The download from NYC Open Data is a single 1.27 GB zip. Inside is one raster in ERDAS IMAGINE format (also called HFA, for Hierarchical File Architecture), the format of a 1990s remote-sensing package that is still common in government GIS shops. An IMAGINE raster is not one file but a family of sidecar files that share a name.

One member, read byte by byte

Every member starts with a 30-byte local file header. Classic zip fields are 32 bits wide, which caps a member at 4 GB, so the .ige uses the Zip64 extension: both size fields say ff ff ff ff, meaning “look in the extra field”, and a 20-byte extra record carries the real 64-bit sizes. Hover a field to see what it means.

That ratio is why the zip is so small: most of a land cover map is long runs of the same class, and over the water and outside the city every byte is 0. Deflate finds those repeats and replaces them with short back-references.

The catch is that deflate is a single stream. Every back-reference can point up to 32 KB into the past, so to decode byte n you need everything before it. There is no index: to reach the bottom row of Staten Island you must decompress the 97 GB above it. Reading front to back is cheap. Seeking backwards means starting over.

The .img header: a tree of typed nodes

The 9.6 KB .img starts with the magic string EHFA_HEADER_TAG, then a pointer to a tree of nodes. Each node has a name, a type, a data pointer and child and sibling pointers; its data is a packed C-style struct whose layout is described by a dictionary also stored in the file. The script walks this tree with hfa_nodes() and reads just three nodes.

Map_Info gives the projection by name only, “NAD83 New York State Planes, Long Island, US Foot”, which GIS software resolves to EPSG:2263. Coordinates are in US survey feet from a false origin southwest of the city. It stores the center of the upper-left pixel, (912,287.18, 273,618.05); the script shifts by a quarter foot to get the outer corner, (912,286.93, 273,618.30).

The .ige: a header, a bitmap, then 23.9 million blocks

The pixel file is the dumbest possible layout, which is what makes it streamable. It begins with its own magic string and a copy of the dimensions:

  • Format constantsNot used by the reader
  • Layers: 1A single band of class values
  • 310,844 × 314,414 pixelsMust match the .img or the script stops
  • Blocks: 64 × 644,096 bytes each, one byte per pixel
  • Block map header, at byte 494,913 rows × 4,857 columns of blocks

The .rrd and .rde hold pyramids, eleven pre-shrunk copies at 1, 2, 4, … ~1024 ft. The script ignores them. They were built by nearest neighbour, keeping one arbitrary pixel out of each group, so a 4 ft pyramid cell might be a single leaf in the middle of a parking lot.

How a GeoTIFF works

TIFF dates from 1986 and is built around one idea: a short header pointing to a list of numbered tags. Width, height, compression, and where the pixel data lives are each just a tag. A reader skips tags it doesn't recognize, which is how GeoTIFF added maps to TIFF in 1995 without breaking anything: it is plain TIFF plus a few extra tags that say where on Earth the pixels are.

Tiles are the whole point

The zip has one compressed stream for 98 GB. The GeoTIFF has ten thousand small ones, and the tile offset table says exactly where each one starts. To draw Columbus Circle, QGIS computes which tiles cover it, reads those few kilobytes, and inflates only them. Zooming and panning cost the same anywhere in the city. That random access is what makes the output feel instant when the source is unworkable.

The conversion

The design follows from one constraint: the source can only be read cheaply from top to bottom. So the script reads it exactly once, top to bottom, and produces every requested resolution from the same pass. Memory stays near one strip of rows rather than the 98 GB image.

  1. Read the header straight out of the zip

    Python's zipfile inflates the 9.6 KB .img. read_source() walks its node tree and pulls out the size, the 64 × 64 block layout, the .ige file name and data offset, and the georeferencing, checking each against what the script expects.

  2. Decompress the .ige on every core

    ZipMember exposes the member's raw deflate bytes, starting at byte 130 of the zip, as a file object. rapidgzip decodes it in parallel, which plain deflate does not normally allow: worker threads jump ahead, guess where deflate blocks begin, and decode with placeholders for the 32 KB of history they don't have yet, filling them in once the earlier chunk finishes. Nothing is written to disk.

  3. Reassemble rows in strips

    Pixels.read_into() reads one block row at a time (19.9 MB), sets any block the bitmap marks invalid to nodata, transposes it into 64 image rows, and hands rows out in strips. A strip is the smallest multiple of every requested block size that is at least 192 rows, so no output pixel is ever split between strips: 192 rows for 1, 3 or 6 ft. A background thread decodes strip i + 1 while strip i is being processed.

  4. Vote each F × F block down to one pixel

    For an output resolution of r ft, F = r / 0.5, so 3 ft means 6 × 6 = 36 source pixels per output pixel. Each output pixel takes the most common class among them. Nodata doesn't vote, an all-nodata block stays nodata, and ties go to the lower class number. The strip is split into one column chunk per CPU and voted in parallel.

  5. Tile, compress and write

    TiledWriter collects output rows until it has a full row of 512 × 512 tiles, then queues them to tifffile, which deflates tiles on worker threads and records their offsets. When the last row arrives, the GeoTIFF tags are already in place and the file is done.

The counting is written to stay inside numpy's fast paths. Up to F = 15 a block has at most 225 pixels, so a count fits in one byte: for each class the script makes a byte mask, adds every F-th column to its neighbours with strided slices, then every F-th row, and keeps the class whenever its count beats the best so far. Using a strict “greater than” is what sends ties to the lower class.

What the vote does and doesn't preserve

  • Each cell gets its dominant cover. Unlike the nearest-neighbour pyramids, a cell that is mostly tree canopy reads as tree canopy.
  • Thin and small features lose area. A railroad 10 ft wide rarely wins a 16 ft cell. Measure class areas on the 6 in source, not on these files.
  • Any valid pixel outvotes nodata, so shorelines and the city boundary grow slightly outward at coarser sizes.
  • Ties favour lower class numbers, so tree canopy (1) wins every tie it is part of.
  • Edges are padded. Sizes round up, so an output can reach up to r − 0.5 ft further east and south than the source; that margin is nodata.
